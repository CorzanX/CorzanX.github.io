Assignment 4 Report: Thesis Sky Defender

Student Name: Zheng Chen
Student ID: ZY2557201
Submission Date: 2026-06-24

1. Assignment Goal

The goal of Assignment 4 is to develop a functional software application with LLMs as the main development partner. I chose Option A: “Defend Your Thesis” (The Game) and implemented it as a WeChat Mini Game instead of a normal browser page.

My final project is called Thesis Sky Defender. It is a mobile survival shooting game where the player controls a fighter to defend the research process from incoming academic threats such as Bugs, Deadlines, Runtime Errors, Reviewers, and a recurring Boss named Major Revision.

The main reason I chose WeChat Mini Game is that it makes the project feel closer to a real mobile application. The game can run in WeChat Developer Tools and can also be previewed on a phone through WeChat. This made the presentation more convincing than only opening a local web page.

2. Project Overview

The player drags the fighter on the screen. The fighter fires automatically, so the core challenge is to move, dodge, use skills, and survive longer.

The gameplay loop is:

  1. Normal enemies continuously enter from the top of the screen.
  2. The player destroys enemies to gain score and skill energy.
  3. If a normal enemy escapes through the bottom, the player loses HP.
  4. After a period of time, a Boss appears.
  5. The Boss actively fires bullets while normal enemies continue to spawn.
  6. Only after defeating the Boss can the player choose an upgrade.
  7. The next Boss becomes stronger, so the difficulty gradually increases.

5. Game Design

5.1 Player

The player controls a neon fighter. The fighter has:

  • HP
  • Shield
  • Skill energy
  • Auto-fire bullets
  • Upgradeable bullet damage, fire rate, bullet count, piercing, and critical chance

The player does not need to press a fire button. This design fits mobile play better because the player’s attention can stay on movement and skill timing.

5.2 Normal Enemies

There are four normal enemy types:

Enemy Design Meaning Gameplay Role
Bug Drone Small implementation bugs Basic enemy
Deadline Time pressure Fast enemy
Runtime Error Severe program failure High-HP enemy
Reviewer Peer review pressure Moving enemy

If a normal enemy is not defeated and escapes through the bottom of the screen, the player loses HP. This rule makes the game more defensive: dodging alone is not enough, and the player must actively clear threats.

5.3 Boss

The Boss is called Major Revision. It appears periodically and creates the main progression checkpoint.

The Boss has three important features:

  • It actively shoots aimed bullets at the player.
  • It fires spread bullet patterns.
  • It becomes stronger after each defeat.

5.4 Upgrade Rule

The game originally considered score-based leveling, but I changed the rule after testing the game feel. The final design is Boss-gated progression:

  • The player cannot upgrade just by killing normal enemies.
  • The player must defeat a Boss to open the upgrade selection.
  • Each Boss defeat increases the player level.
  • Later Bosses have higher HP, damage, movement range, and bullet density.

This creates a clearer rhythm: survive, fight Boss, upgrade, then face a harder wave.

5.5 Skills

The game has two active skills:

Skill Cost Effect
Shield 35 energy Restores the player’s shield
EMP 60 energy Clears normal enemies and Boss bullets; also damages the Boss

The EMP skill is especially useful during Boss bullet bursts. This adds decision-making instead of making the game only about movement.

6. Software Architecture

The code is organized around a simple game loop: update game state, check collisions, and render the scene.

6.1 Main Loop

The main loop is implemented with requestAnimationFrame. Each frame performs:

  1. timer update
  2. background update
  3. player update
  4. bullet update
  5. enemy update
  6. enemy generation
  7. collision detection
  8. rendering

This structure made the later feature additions easier because most new features could be inserted into one clear phase of the loop.

6.2 State Management

The DataBus module stores global game state, including:

  • score
  • HP and shield
  • energy
  • wave
  • Boss status
  • current phase: menu, playing, upgrade, or gameover
  • player upgrades
  • object arrays and object pool

Keeping these values in one place reduced the chance of inconsistent state between UI, player, enemies, and collision logic.

6.3 Boss Scaling

The Boss is generated in main.js. Its level is calculated from the number of Bosses already defeated.

This made the difficulty curve simple but effective. Later Bosses survive longer, hit harder, move more, and fire denser patterns.

6.4 Enemy Leak Damage

To make normal enemies meaningful during Boss fights, I added leak damage. If a normal enemy leaves the bottom of the screen, the player loses HP directly.

This prevents the player from ignoring normal enemies and only focusing on the Boss.

7. AI-Assisted Development Process

7.1 Planning the Game

At the beginning, I used the LLM to turn the vague idea of “a plane shooting game” into a complete rule set. The AI helped me compare possible directions and suggested a thesis-defense theme that matched the assignment topic.

The early design included:

  • player movement
  • automatic shooting
  • enemy waves
  • HP and score
  • skills
  • Boss fights
  • upgrade choices

Then I refined the rules manually based on gameplay logic. For example, I changed the upgrade condition from normal leveling to Boss-gated upgrading because it made the progression clearer.

7.2 Choosing WeChat Mini Game

I first considered making a normal web game. After discussion with the AI, I switched to WeChat Mini Game because:

  • it is more distinctive for a class presentation;
  • mobile drag control fits the game genre;
  • it can be previewed on a real phone;
  • the WeChat Mini Game template already provides a suitable Canvas environment.

The AI helped me identify the project files, understand the Mini Game runtime, and adapt the game loop to WeChat APIs.

7.3 Implementing Features

The LLM was used as a development partner for several concrete tasks:

Feature AI Assistance
Player movement Helped adapt touch control to mobile gameplay
Collision detection Helped reason about bullet-enemy, player-enemy, and player-Boss bullet collisions
Boss attacks Helped design aimed bullets and spread bullets
Upgrade system Helped design upgrade options and connect them to player stats
Skill system Helped implement Shield and EMP with cooldown and energy cost
HUD Helped organize HP, shield, energy, score, wave, Boss timer, and skill buttons
Art direction Helped choose a neon sci-fi theme and generate consistent assets
Package size Helped find and exclude large non-game files to stay under WeChat limits

7.4 Handling AI Mistakes and Debugging

The AI was useful, but I did not directly trust every suggestion. Several issues had to be checked and corrected.

Issue Problem Fix
Package size exceeded 4 MB The first mobile debugging attempt failed because the project package was too large Compressed the background image and excluded presentation/template/tool files from the Mini Game package
iOS remote debugging iOS showed that the current version did not support Mini Game remote debugging Used phone preview instead of remote debugging
Phone notch blocked HUD HP and other parameters were too close to the top safe area Added safe-area handling and moved HUD downward
Report/presentation layout Some Beamer text was covered Rebuilt several slides with shorter text and safer layout
AI code suggestions Some suggestions needed adaptation to WeChat Mini Game APIs Checked syntax, file paths, runtime behavior, and official API compatibility

One important lesson is that AI can accelerate implementation, but debugging still requires engineering judgment. The final result came from an iterative process: ask, implement, run, observe, and revise.

8. Embedded AI Assistant

The game includes a lightweight in-game AI Assistant on the result screen. It is not a cloud LLM call, because that would require network configuration and API keys inside a Mini Game. Instead, I implemented a local rule-based assistant that reads player performance and gives contextual advice.

The assistant checks data such as:

  • number of Bosses defeated
  • kill count
  • survival time
  • score
  • high score

10. Reflection

This assignment helped me understand the difference between using AI for small code snippets and using AI as a software development partner.

The most useful part of AI assistance was not only generating code. It was more valuable for:

  • breaking a vague idea into modules;
  • comparing design choices;
  • finding missing gameplay rules;
  • debugging runtime issues;
  • improving presentation and documentation.

At the same time, the project also showed the limits of AI-assisted coding. The LLM did not automatically know the exact state of my WeChat Developer Tools, mobile environment, or package size restrictions. These problems required real testing and manual judgment.

Overall, the final game is small, but it has a complete loop: play, survive, fight Boss, upgrade, and retry. More importantly, it is implemented as a WeChat Mini Game, which makes it closer to a real mobile application than a simple classroom web demo.

11. Future Improvements

If I continue improving this project, I would like to add:

  • more Boss attack patterns;
  • real character selection;
  • more sound effects and hit feedback;
  • a ranking screen;
  • a tutorial page;
  • a real LLM-powered assistant connected through a safe backend service;
  • an online experience version for more classmates to test.

12. Conclusion

Thesis Sky Defender satisfies the core requirement of Assignment 4: it is a functional application developed with AI assistance. It also extends the original “Defend Your Thesis” idea into a mobile WeChat Mini Game with Boss fights, upgrades, skills, and an embedded assistant.

Through this project, I practiced not only JavaScript and Canvas game development, but also a more realistic AI-assisted workflow: designing with AI, implementing with AI, testing by myself, and correcting the system when the first answer was not enough.
